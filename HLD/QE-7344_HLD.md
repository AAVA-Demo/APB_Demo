#### 1. High-Level Design

**Summary:**  
This epic delivers an end-to-end real-time fraud detection and alert orchestration system for credit card transactions. It ingests transaction events from the authorization platform, evaluates risk using a fraud-risk engine, creates canonical fraud-alert records, manages alert lifecycle states, and delivers notifications to customers via multiple channels (push, SMS, email, in-app). The system ensures idempotent processing, provides operational monitoring, and maintains audit trails while meeting strict latency and availability requirements for security-critical operations.

**Component Flow:**

```mermaid
flowchart LR
    A["Card Authorization Platform"]
    B["Transaction Event Ingestion"]
    C["Fraud Risk Engine"]
    D["Policy Decision Engine"]
    E["Alert Service"]
    F["Notification Delivery Service"]
    G["Analytics and Audit Service"]
    H["Customer"]
    I["Operations Dashboard"]
    
    A --> B
    B --> C
    C --> D
    D --> E
    E --> F
    F --> H
    E --> G
    G --> I
```

**Integration Points:**
- **Upstream Systems:**
  - Card authorization/transaction platform (source of transaction events)
  - Fraud-risk engine/model (provides risk scoring)
  - Policy/decision engine (configurable alert thresholds and treatment rules)
  
- **Downstream Systems:**
  - Notification providers (push, SMS, email, in-app channels)
  - Analytics, monitoring, and audit infrastructure (event capture and operational visibility)
  - Customer-support stakeholders (for alert delivery status and operational dashboards)

**Key Assumptions:**
1. Transaction events arrive in a standardized format containing transaction_id, account_id, card_id, merchant, amount, currency, timestamp, and channel; the authorization platform provides reliable event delivery with retry mechanisms.
2. The fraud-risk engine returns risk scores and decisions synchronously or within the agreed transaction-time SLA; model versioning is tracked externally and provided with each risk decision.

**NFR Highlights:**  
Risk evaluation and alert triggering must meet agreed transaction-time SLA; security-critical alert services require high availability with defined disaster recovery; system must support transaction spikes without unacceptable alert delays; strong authentication, encryption, secrets management, and least privilege apply throughout.

**Data Flow:**  
Transaction events flow from the card authorization platform into the transaction event ingestion service, which validates and normalizes the data. Each transaction is evaluated by the fraud-risk engine, which returns a risk score and decision. The policy decision engine applies configurable thresholds to determine if an alert is required. If triggered, the alert service creates a canonical fraud-alert record with a unique alert_id and transitions it through defined lifecycle states (Created → Queued → Delivered → Viewed/Confirmed/Reported → Resolved). The notification delivery service attempts delivery via the customer's preferred channel (push, SMS, email, in-app) with fallback logic if the primary channel fails. All alert creation, delivery attempts, delivery status, and failures are captured as analytics events and written to the audit trail. Operational monitoring dashboards consume these events to provide real-time visibility into alert and notification performance, including latency metrics, delivery success rates, and error conditions.

#### 2. Validation Report

**Requirements Coverage:**  
The design comprehensively covers all functional requirements specified in the epic:
- **FR-01 (Transaction ingestion):** Transaction event ingestion service receives eligible events from the authorization platform.
- **FR-02 (Risk scoring):** Integration with the approved fraud-risk engine for transaction evaluation.
- **FR-03 (Alert threshold):** Policy decision engine applies configurable risk thresholds.
- **FR-04 (Notification):** Notification delivery service supports push, SMS, email, and in-app channels.
- **FR-05 (Transaction context):** Alert records include transaction amount, merchant, time, location, and card context as defined in the PRD.
- **FR-09 (Audit trail):** Analytics and audit service records alert creation, delivery, viewing, and failures.
- **FR-10 (Idempotency):** Alert service implements idempotency handling using transaction_id to prevent duplicate alert creation.
- **FR-11 (Fallback):** Notification delivery service includes fallback channel logic when primary channels fail.
- **FR-12 (Preferences):** System respects customer notification preferences subject to security policy overrides.
- **FR-13 (Status):** Alert service maintains alert lifecycle states for customer visibility (active and recently resolved alerts).
- **FR-14 (Operations visibility):** Operations dashboard provides authorized fraud operations users with alert outcome investigation capabilities.

The design also addresses all non-functional requirements including latency SLAs, high availability, security controls (authentication, authorization, encryption, secrets management, least privilege), reliability mechanisms (idempotency, retries, event versioning, durable audit records), scalability for transaction spikes, privacy controls for sensitive data exposure and retention, observability (metrics, logs, traces, alert delivery status, operational dashboards), and accessibility across supported platforms.

**Scope Alignment:**  
The design is fully aligned with the epic's defined scope:
- Transaction event ingestion from authorization platform ✅
- Risk scoring integration and configurable alert thresholds ✅
- Alert creation and canonical fraud-alert record management ✅
- Alert state model and lifecycle transitions ✅
- Notification delivery via push, SMS, email, and in-app channels ✅
- Alert content including transaction details and plain-language risk message ✅
- Fallback notification behavior when preferred channels fail ✅
- Respecting customer notification preferences subject to security policy ✅
- Idempotency handling to avoid duplicate alerts or cases ✅
- Analytics events for alert creation, delivery, viewing, and failures ✅
- Operational monitoring of alert and notification performance ✅

The design explicitly excludes out-of-scope items: building a complete enterprise fraud-management platform, guaranteeing zero fraudulent transactions, replacing all existing fraud models, cross-product identity fraud detection, international expansion with market-specific regulatory workflows, advanced machine-learning model development, and customer-facing explanation of exact fraud-model features or scores.

**Dependency Management:**  
All dependencies identified in the epic are addressed in the design:
- Card authorization/transaction platform: Integrated via transaction event ingestion service
- Fraud-risk engine/model: Integrated for risk scoring
- Policy/decision engine: Integrated for configurable thresholds and alert decisions
- Notification providers: Integrated via notification delivery service with multi-channel support
- Analytics, monitoring, and audit infrastructure: Integrated via analytics and audit service
- Security, legal, compliance, and customer-support stakeholders: Addressed through security controls, audit trails, and operations dashboard

**Risk Mitigation:**  
The design incorporates mitigations for key risks:
- **False positives:** Configurable thresholds in policy decision engine allow tuning; analytics capture confirmed-legitimate responses for continuous improvement
- **Alert delays:** Latency monitoring and scalability design ensure transaction spikes don't cause unacceptable delays
- **Notification delivery failures:** Fallback channel logic and retry mechanisms with delivery status tracking
- **Duplicate processing:** Idempotency handling using transaction_id prevents duplicate alert creation
- **Service unavailability:** High availability design with disaster recovery for security-critical services; fail-safe policies for risk engine unavailability
- **Sensitive data exposure:** Encryption in transit and at rest, least-privilege access, approved retention/deletion policies, minimal sensitive data in logs

**Acceptance Criteria Validation:**  
The design satisfies all acceptance criteria from the PRD:
- ✅ Eligible suspicious transactions crossing alert threshold create alerts
- ✅ Alerts trigger delivery attempts through configured channels with delivery status recording
- ✅ Alert lifecycle transitions are captured in audit records
- ✅ Idempotent processing prevents duplicate cases from duplicate transaction events
- ✅ Notification provider failures trigger retry/fallback policy
- ✅ Risk engine unavailability follows predefined fail-safe policy with condition recording
- ✅ Operational monitoring provides end-to-end transaction-to-alert and alert-to-protection performance visibility

**Operational Readiness:**  
The design includes comprehensive operational monitoring capabilities:
- Transaction-to-risk-decision latency metrics
- Alert creation rate and error rate tracking
- Notification delivery success by channel/provider
- Analytics events for alert lifecycle transitions (creation, delivery, viewing, failures)
- Operational dashboards for authorized fraud operations users
- Model performance and version tracking (integrated with fraud-risk engine)

**Conclusion:**  
The High-Level Design for Epic QE-7344 provides a complete, validated architecture for real-time fraud detection and alert orchestration. All functional and non-functional requirements are addressed, dependencies are integrated, risks are mitigated, and operational monitoring is comprehensive. The design is ready for detailed technical specification and implementation planning.
